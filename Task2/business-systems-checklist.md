# Task2 — Проверочный лист бизнес-систем PropDevelopment

Артефакт подготовки к аудиту ИБ. Источники: кейс PropDevelopment, C4-контейнеры, выводы Task1 (классы данных / критичность ПДн). Шаблон вопросов — `IB.md`.

| ЖКУ     | `tenant-core-app` + БД                              | услуги УК, платежи ЖКУ; confidential ПДн (Task1)                                    |

| ЖКУ     | API УК (партнёры)                                   | внешний периметр без единых политик; кросс-доступ между УК; лишние ПДн в контрактах |

| Дата    | хранилище / BI / отчётность                         | агрегация потоков, в т.ч. ПДн; **нет ограничений доступа** (явная боль кейса)       |

Связь с болями кейса: несколько точек регистрации клиента без координации; потоки между продуктами без системного контроля; Data без ACL (блок на BI/ML); партнёрские API без политик и с кросс-tenant доступом; жалобы на чужие ФИО в ЛК; один специалист ИБ и разорванная передача решений.

Из Task1: клиентские/собственнические ПДн и ПДн у партнёра УК — confidential с критическими рисками утечки/искажения; «секрет» — данные онлайн-сделки и госинтеграций. Mindmap не дублируем — опираемся на классы критичности.

## 2. Выбор разделов

### Включаем полностью

**I. Управление доступом**  
Путаница в ЛК = сбой authZ (чужой субъект в сессии/контексте). Партнёр одной УК видит/меняет данные другой. В кейсе нет least privilege и единого IdP. Несколько точек регистрации клиента → нет единого реестра УЗ. Один ИБ + дыры в передаче решений → нужны MFA на критичных контурах, RBAC, реестр УЗ, журналы, отзыв прав, жёсткое ограничение внешнего доступа (особенно API УК).

**II. Безопасность данных**  
Главная боль: ПДн, нет классификации и ограничений потоков, Data-домен открыт, блок на BI/ML, проверка ФЗ-152. Бэкапы БД в кейсе уже есть — заполняем по факту (наличие vs шифрование/тесты восстановления).

**III. Защита инфраструктуры**  
Firewall снаружи есть; гибрид (свой ЦОД + приватное + арендованное облако). Нужна сегментация и фильтрация между доменами и партнёрским контуром — иначе API УК и Data остаются в «плоской» зоне доверия.

**IV. Управление инцидентами**  
Утечка у конкурента, один ИБ, подготовка к аудиту. Без SIEM/IR/учений аудит будет формальным: некому системно ловить кросс-tenant и утечки ПДн.

### V — только облачный срез V.1

Гибрид и арендованное облако → вопросы про cloud backup / контроль копий. VPN/удалёнка — данных мало → `Н/Д` с пометкой для аудита.

### Исключаем

| Что                         | Почему                                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **V.1 MDM / rogue devices** | В кейсе нет корпоративного мобильного парка сотрудников. Мобилка собственников — продуктовый клиент, не MDM.       |
| **V.2 физбезопасность ЦОД** | Свой ЦОД упомянут, но фактов (СКУД, инвентаризация) нет. Не закрывает две главные боли (данные + партнёрские API). |

**Лучше для PropDevelopment (направление, не объём Task3–5):** 
 - централизованный IdP + RBAC; 
 - default-deny между сегментами доменов и партнёров; 
 - классификация + ACL на Data; 
 - контрактный контроль партнёрских API (минимум ПДн, запрет кросс-УК).
