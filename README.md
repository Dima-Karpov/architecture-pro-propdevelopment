# PropDevelopment — безопасность и подготовка к аудиту

Проектная работа пятого спринта курса «Архитектор ПО» (Яндекс Практикум).

Крупный застройщик готовится к комплексному аудиту безопасности. Нужно навести порядок в данных, интеграциях и доступе в Kubernetes — без этого компания не может спокойно развивать сервисы для клиентов и собственников.

## О компании

**PropDevelopment** — топ-3 застройщик в стране. Работает в основном с частными клиентами:

- **клиенты** — ещё выбирают и покупают жильё;
- **собственники** — уже купили и живут в комплексах компании.

Для клиентов есть онлайн-витрина, онлайн-тур по квартире и онлайн-сделка. Для собственников — мобильное приложение: ЖКУ, ремонт, связь с УК и «Умный дом».

Внутри четыре домена:

| Домен | Что внутри |
| --- | --- |
| Продажи | витрина, онлайн-тур, онлайн-сделка, CRM клиентов, данные по недвижимости |
| ЖКУ | сервисы для собственников, CRM жильцов, интеграции с управляющими компаниями |
| Финансы | учёт и каталоги |
| Дата | хранилище, BI, отчётность |

Инфраструктура смешанная: свой ЦОД, приватное облако и иногда облако провайдера. Снаружи вход через firewall.

## Зачем этот проект

У компании две главные боли:

1. **Данные разъехались.** Клиента можно завести в нескольких местах, потоки между системами почти не контролируются, доступ к данным слабо ограничен. В кабинете иногда мелькают чужие Ф. И. О.
2. **Партнёрские API без единых правил.** Системы УК подключены как получится: в контрактах лишние ПДн, иногда партнёр одной УК видит чужие ЖК.

Плюс руководство смотрит на утечки у конкурентов и хочет проверить соответствие законодательству перед ростом BI/ML-продуктов.

Аудит — способ закрыть эти дыры до того, как они станут инцидентом.

## Как устроен репозиторий

Публичный репозиторий. Семь каталогов — по одному на задание. Сдача — **один PR** со всеми решениями. После отправки ссылки на ревью правки не вносим, пока не ответит ревьюер.

Схемы из `.puml` собирает [GitHub Actions](.github/workflows/plantuml.yml) в SVG и коммитит обратно в ветку при push. Обычно C4 кладём в `Task3/c4/*.puml`.

### Задание 1. Mindmap безопасности данных

Классификация данных PropDevelopment по ISO/IEC 27001/27002 (public / internal / confidential / secret), риски и оценка. Mindmap в draw.io → `Task1`.

### Задание 2. Проверочный лист бизнес-систем

Список систем, выбор разделов чеклиста под боли кейса (с обоснованием), заполненная Markdown-таблица → `Task2`.

### Задание 3. Внешние интеграции «Умного дома»

Партнёр даёт интеллектуальный домофон (в т.ч. биометрия) и шлагбаум (номера авто). Нужны C4 Context, обновлённые Containers и требования к безопасности, authN/authZ и взаимодействию → `Task3`.

### Задание 4. RBAC в Kubernetes

Таблица ролей под оргструктуру и три скрипта: users / roles / bindings → `Task4`.

### Задание 5. Сетевые политики

Четыре nginx с labels `role`: front↔api и admin-front↔admin-api, перекрёст закрыт → `Task5`.

### Задание 6. Audit log

Разбор инцидента по audit.log: `analysis.md`, `audit-extract.json`, скрипт фильтрации → `Task6`.

### Задание 7. PodSecurity и Gatekeeper

Namespace `audit-zone`, insecure/secure манифесты, constraint'ы Gatekeeper и проверка → `Task7`.

## Что должно лежать в PR

| Каталог | Содержимое |
| --- | --- |
| `Task1` | mindmap draw.io: категории данных, риски, оценки |
| `Task2` | проверочный лист бизнес-систем (Markdown) |
| `Task3` | C4 context + containers, требования к интеграциям |
| `Task4` | таблица ролей + скрипты users / roles / bindings |
| `Task5` | NetworkPolicy (yaml) |
| `Task6` | `analysis.md`, `audit-extract.json`, скрипт фильтрации |
| `Task7` | PodSecurity + Gatekeeper + verify |

Задания 4–7 опираются на выводы 1–3: какие данные критичны, какие роли нужны, как резать внешние интеграции.
